## Reproduction and comparison

```bash
pnpm build
pnpm measure:publication-candidate > tmp/v1.1-publication-candidate-v3-final-run-1.json
pnpm measure:publication-candidate > tmp/v1.1-publication-candidate-v3-final-run-2.json
pnpm measure:publication-candidate:compare tmp/v1.1-publication-candidate-v3-final-run-1.json tmp/v1.1-publication-candidate-v3-final-run-2.json
```

The ephemeral server exposes only `dist/` below `/Mundus/` and closes in
`finally`. Sample cleanup attempts CDP, page, context, and browser closure in
order and aggregates errors, so one close failure cannot skip later resources.
There is no intentional-abort request exemption: any failed request recorded by
the page fails validation. Console/page errors and unexpected duplicate asset
fetches also fail; warnings remain recorded. Every sample must explicitly carry
array-valued console-error, page-error, request-failure, and duplicate-fetch
evidence, even when each array is empty; omitted or malformed evidence fails
schema validation.

The comparator requires distinct execution IDs and exact equality for schema,
scenario, Git HEAD, environment (including browser and network state), complete
asset identity, and each scenario context (viewport, DPR, locale, user agent,
mobile/touch signals). It permits raw timings to differ. Both executions matched
all provenance and selected desktop 50m / Pixel 110m across all samples.

## Observation semantics

Immediately after `DOMContentLoaded`, the runner starts two independent
`waitForFunction` condition pollers together with `Promise.all`:

- globe usable: vector state is ready and renderer calls are at least four;
- decoded bilateral/index ready: `data-antipode-relation-state="ready"`.

The timestamps are when each browser condition poller observed its condition,
not exact internal state-transition events. No app event exists for those
transitions, so condition-observation timing is the honest available semantic.
Concurrent polling avoids delaying bilateral/index observation behind globe
readiness. The observation-start timestamp and both independent observation
times are retained per sample and schema-validated.

GeoNames starts during initial Other Side because bilateral relations and search
share one index. The report records its navigation-relative request start,
response, transfer, and decoded bilateral/index observation, then separately
measures warm first-focus search from focus plus `Tokyo` input to first visible
option. Exactly one GeoNames resource is required per clean run.

Immediately before Development click, resource entries are captured and
`developmentEntryAtMs` is recorded. Control JS, CSS, and UNDP data must all be
absent then, must each start at or after entry, and readiness requires visible
global-median evidence. No fixed sleep is a measurement source.
